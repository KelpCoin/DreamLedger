# BrownEye Cortex / DreamLedger
# Refined Execution Plan: The Domino Economic Engine
## Canonical Strategic Doctrine

**Status:** CANONICAL NORTH STAR  
**Date adopted:** 2026-09-20 NZST  
**Purpose:** Governing doctrine for BrownEye Cortex / DreamLedger execution.

> Reality is canonical in outcome. Architecture is subordinate to economic reality.

This document is doctrine, not a software specification and not a requirement to build architecture for its own sake. Code, databases, agents, protocols, dashboards, workers, and integrations are subordinate implementation tools. They are justified only when they create economic evidence, protect economic truth, or materially reduce the cost or risk of creating the next piece of economic evidence.

## 1. Core objective

Create a repeatable system that discovers a real economic opportunity, produces something a real buyer can use, causes an external economic event, verifies what actually happened, learns from the result, and uses that evidence to improve the next attempt.

Canonical loop:

**Opportunity -> Buyer -> Mission -> Artifact -> External Effect -> Outcome -> Evidence -> Learning -> Replication**

The system earns the right to scale through evidence.

Optimize for **economic evidence velocity**, not code velocity.

## 2. The immediate operating unit

The first economic loop is deliberately tiny:

**One existing opportunity -> one named buyer -> one scoped deliverable -> one authorized external action -> one recorded outcome.**

If the opportunity is stale, invalid, inaccessible, or not genuinely executable, kill, supersede, or quarantine it and record why.

Do not build infrastructure to rescue a bad opportunity unless that work is itself the smallest demonstrated route to an external effect.

## 3. Anti-theatre rule

Before building anything, ask:

1. Does it unlock an external economic transition?
2. If not, does it materially reduce the cost or risk of a transition we already know we need?
3. If not, does it create evidence required to choose the next transition?

If all three are no, defer it.

Preparation is not automatically progress.

The roadmap is a decision graph, not a prerequisite chain. Domino numbers are coordinates, not gates.

## 4. Economic truth invariant

Internal state must never impersonate external state.

**AUTHORIZED != SENT**  
**SENT != RECEIVED**  
**RECEIVED != ACCEPTED**  
**ACCEPTED != PAID**  
**PAID != FULFILLED**  
**FULFILLED != VERIFIED**  
**VERIFIED != BUSINESS_TRUTH unless the required independent chain is established.**

A payment route is not commerce. A database row is not a buyer. A model output is not a customer response. A test event is not revenue.

The system must prefer "nothing happened" over invented success.

## 5. Evidence hierarchy

Weak evidence:

idea, capability, prototype, internal test, generated artifact, qualified opportunity, buyer identified, deliverable prepared.

Stronger evidence:

deliverable sent, buyer response, buyer acceptance, payment intent, payment initiated.

Very strong evidence:

settled external payment, correct attribution, fulfillment, independent verification, repeat purchase, referral, repeated demand.

A non-response, rejection, failed transaction, stale opportunity, or competitive loss is still evidence when accurately recorded. It is not equivalent to success.

## 6. No Buyer, No Mission

A mission must be economically anchored where applicable by:

- opportunity
- buyer reference
- buyer source
- buyer request
- deliverable
- price/payment expectation
- fulfillment method
- evidence requirement
- authorization status

A capability without a buyer is research.

A mission without a buyer is architecture masquerading as execution.

The deliverable is the meaningful unit of production progress: buyer-specific, scoped, inspectable, useful, attributable, reproducible, deliverable, and evidence-producing.

## 7. Roles

**Elohim proposes.**  
Candidate solutions, deliverables, opportunity interpretations, production approaches, optimization hypotheses.

**Gauntlet judges.**  
Truth, voice/form, usefulness, attention/clarity, and whether a real economic path exists.

**Truth Oracle answers:** "What do we actually know?"

Truth Oracle does not convert plausibility into fact.

Evidence labels include:

VERIFIED, UNVERIFIED, CONTRADICTED, STALE, TEST, SIMULATED, INTERNAL, UNMATCHED.

**Gemini is an experimental high-context decision instrument.** Its output is input/evidence, not economic authority. Cortex reconciles it against production reality. Gemini's economic advantage is unproven until measured.

**ChatGPT / Cortex** maintains strategic state, reconciles evidence, performs controlled implementation and verification, and reduces future human work.

**Supabase** is durable economic memory.

**GitHub** is the implementation/evolution substrate. Code changes must correspond to real bottlenecks or protection of economic truth.

**Stripe** is settlement authority.

**Browser** is an external actuator when authenticated platform interaction is required. A disconnected browser is a capability constraint, never permission to fabricate completion.

## 8. Economic state model

Broad lifecycle:

DISCOVERED -> NORMALIZED -> EVIDENCED -> TRIANGULATED -> QUALIFIED -> OFFERABLE -> AUTHORIZED -> EXECUTING -> EXTERNAL_EFFECT -> PAYMENT_PENDING -> SETTLED -> FULFILLING -> FULFILLED -> VERIFIED -> BUSINESS_TRUTH -> LEARNED -> REPLICABLE

Exception/terminal states include:

STALE, CONTRADICTED, FAILED, REJECTED, QUARANTINED.

This is an operational model, not a rigid ontology. Evidence may branch, roll back, supersede, or terminate a path.

## 9. CUBE rule

CUBE is not entitled to a master/reference domain before external evidence exists.

The first real economic cell that survives external testing becomes the candidate reference cell.

**Do not clone a hypothesis. Clone verified economic behavior.**

A CUBE may eventually represent:

Demand source + capability + offer + production path + fulfillment path + evidence path + control policy.

Successful mutations survive. Failed mutations become evidence.

## 10. Existing opportunity inventory

Use existing opportunities before inventing new opportunity architecture.

Database qualification is not current market availability.

External freshness matters.

Do not invent a new opportunity merely to avoid confronting failure of an existing one.

## 11. External standards and market claims

Established public standards and market infrastructure must be inspected and reused where applicable rather than reinvented.

Agentic-commerce infrastructure such as x402, ERC-8004, A2A registries, agent marketplaces, and similar systems are hypotheses about commercial maturity, not proof of mature paying demand.

Verification is an existing competitive market, not an assumed empty category.

Palantir is an architectural analogy, not commercial evidence for DreamLedger.

Multi-model routing is an experiment, not doctrine.

Research claims must be independently verified from current sources before they drive consequential decisions.

## 12. Overnight autonomy

Cloud systems may safely:

- scan sources
- refresh evidence
- detect stale opportunities
- reconcile payments
- inspect execution packets
- run deterministic verification
- run model tasks
- repair known-safe implementation defects
- classify outcomes
- update ledgers
- prepare approval packets
- quarantine contradictions
- select candidates

They stop at genuine external authority boundaries.

The objective is safe continuous progress, not total autonomy.

## 13. Human attention

Optimize for:

> What is the smallest human action that unlocks the largest external economic transition?

Preferred interface:

**ONE ACTION REQUIRED:** approve the specific external action.

Then:

**DONE:** record exactly what happened and what evidence exists.

The human increasingly handles genuine authority boundaries and high-leverage decisions, not repetitive mechanics.

## 14. One action, one outcome

Every cycle should seek one action and one observable outcome.

Examples:

Send artifact -> buyer response or non-response.

Kill stale opportunity -> superseded opportunity with evidence.

Reconcile charge -> attributed settlement or UNMATCHED classification.

Run verifier -> artifact matches or fails verification.

This is the heartbeat of execution.

## 15. 25-50 domino roadmap

The approximate roadmap is:

1-5: economic truth and live opportunity selection.
6-10: buyer-specific production and immutable proof.
11-15: buyer/channel confirmation, authorization, external send, external-effect recording.
16-20: response, payment, fulfillment, independent verification, outcome classification.
21-25: failure/success analysis, evidence updates, offer/price learning, next experiment.
26-50: progressive reduction of human work, automation of proven production, replication of verified behavior, parallel experiments only after the single-cell loop works.

The sequence may expand, collapse, branch, reorder, delete, or create dominoes in response to evidence.

Domino count is not a KPI.

## 16. Economic thresholds

**Threshold 1:** one independently verified external economic event.

**Threshold 2:** a transaction repeatable without materially increasing human workload.

**Threshold 3:** a winning economic cell clonable into another opportunity without starting from zero.

These matter more than arbitrary amounts of code or documentation.

## 17. Dashboard priority

Prioritize:

- Verified revenue
- Verified external outcomes
- Settled payments
- Active buyer-backed missions
- Deliverables ready
- External actions pending
- Human approvals required
- Stale opportunities
- Failed experiments
- Repeatable winners

Then show:

**CURRENT DOMINO:** one sentence.  
**NEXT HUMAN ACTION:** one sentence.  
**BLOCKER:** one sentence.

Everything else is secondary.

## 18. Deferred architecture

Genome Registry, artifact-contract expansion, Worker Registry, Capability Leasing, Collision Engine, Metabolic Observer, fitness models, Dealer Hand/resource allocation, Supervisor, Cedar/regression expansion, Russian-doll compiler, large dashboards, generalized protocols, additional marketplace infrastructure, and new agent layers remain deferred unless evidence demonstrates that a component removes a real bottleneck.

Architecture graduates into priority by demonstrated need.

## 19. First economic cell

The target is not a generic platform completion milestone.

The target is a real cell:

**REAL DEMAND -> NAMED BUYER -> MINIMUM DELIVERABLE -> EXTERNAL EFFECT -> RECORDED OUTCOME -> VERIFIED EVIDENCE -> LEARNING -> NEXT ACTION**

Commerce is an observed event inside the loop, never an assumed property of the architecture.

## 20. Doctrine for implementation

When a live buyer-backed opportunity can be acted on with existing capability, prefer the smallest legitimate external action over additional preparation.

When no legitimate external action is available, perform only the minimum work required to create one or establish why none is currently possible.

Every internal engineering action must justify itself against the economic loop.

No architecture expansion merely because it is interesting.

No platform construction merely because a protocol exists.

No claim of demand merely because infrastructure is active.

No claim of revenue without external settlement and the required evidence chain.

No claim of autonomy where a human still performs the consequential external action.

## 21. Canonical adaptive clause

This doctrine is canonical in direction, not sequence.

Canonical means the economic doctrine, evidence hierarchy, authority boundaries, truth requirements, and loop-engineering principles govern execution.

It does not make any particular domino number, implementation, opportunity, technology, market, or architecture permanent.

New evidence may reorder, merge, delete, replace, or create dominoes.

The canonical objective is not completion of this document.

**The canonical objective is increasing verified economic throughput while preserving truth, safety, attribution, and human control over consequential external actions.**

## 22. Operational mantra

**One buyer.**  
**One mission.**  
**One deliverable.**  
**One external effect.**  
**One recorded outcome.**  
**Then learn.**

**Scale only what reality proves.**

## 23. Red-team amendment

This doctrine explicitly supersedes any interpretation that turns the domino map into a long sequence of internal preparation stages before the first external effect.

The first external effect is the immediate bottleneck.

Existing standards must be adopted or explicitly rejected rather than presented as recovered proprietary inventions.

Agentic-commerce market assumptions remain empirical.

Verification remains a competitive market.

Multi-model routing and Gemini are experiments.

Shared substrate is a coordination mechanism, not proof of economic advantage.

Opportunity, commerce, and evidence remain separate.

No designated master/reference domain exists before a real economic cell survives external testing.

The scoreboard begins at reality:

VERIFIED REVENUE: NZ$0  
EXTERNAL EFFECTS: 0  
SETTLED PAYMENTS: 0  
BUSINESSTRUTH RECORDS: 0  
DELIVERABLES SENT: 0  
REPLICABLE CELLS: 0

The immediate operating instruction is always:

1. Select one existing opportunity.
2. Determine whether it maps to a named buyer and a currently reachable external channel.
3. If yes, scope one deliverable and execute the smallest authorized external action.
4. If no, mark it stale, failed, or superseded as appropriate and record why.
5. Do not expand architecture merely because execution is inconvenient.
6. Record the outcome regardless of success, rejection, non-response, or failure.
7. Use that outcome to determine the next action.

**One action. One outcome. Update the graph.**
