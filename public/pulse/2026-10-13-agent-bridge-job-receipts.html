Agent Bridge job receipts: make every paid task prove its own delivery.

An agent marketplace becomes economically trustworthy when a job can be followed from buyer intent to an authorized task, from settled payment to bounded execution, and from output to independently checkable delivery evidence. A green workflow is useful operational evidence, but it is not a customer or a sale.

CURRENT LIVE BOUNDARY: ACCESS PROBE HELD

The existing Agent Bridge page states that the 50-cent probe remains held until verified. Its API manifest is the live contract surface. This artifact specifies the next implementation and acceptance gates; it does not assert that metered GPU jobs, customer checkout, or end-to-end fulfillment are already working.

Sources: Agent Bridge service page · API manifest.

1. Define one durable job contract

Every job needs a stable identifier, a buyer-authorized scope, an input digest, an execution policy, a declared price or budget ceiling, an idempotency key, a deadline, and a delivery contract. The record must distinguish proposal, authorization, funding, execution, submission, evaluation, and terminal outcome. Retrying a request must not create a second charge or silently duplicate expensive work.

Illustrative schema only. A zero budget is a placeholder, not a live price. Production validation must reject missing identity, invalid currency, unsupported task classes, unsafe inputs, and budgets not explicitly authorized by the buyer.

2. Keep the money state separate from the job state

PaymentIntent creation, a Checkout Session, a successful browser redirect, or an internal database row is not settled revenue. The payment adapter must reconcile the provider's settled event to the exact order and offer, then grant only the matching entitlement. Duplicate webhooks must be idempotent. Refunds, disputes, unmatched payments, currency mismatches, and missing fulfillment routes must be quarantined rather than guessed.

  • Payment proof: provider event and balance transaction matched to a unique order and catalog offer.
  • Execution proof: worker identity, policy version, start/end timestamps, bounded resource usage, and exit state.
  • Delivery proof: output digest, object or download reference, acceptance criteria, and evaluator result.
  • Economic truth: a buyer is counted only after payment, fulfillment, and attribution are independently reconciled.

3. Expose GPU capacity as a permissioned worker, not an open shell

A local GPU can be an optional accelerator while the control plane, queue, billing, evidence, and fallback workers remain cloud-hosted. The GPU owner must opt in and be able to revoke availability. A task receives a declared resource envelope, time limit, storage quota, and allowed model/tool list. Arbitrary host access, unrestricted network egress, secrets, persistence between tenants, and uncontrolled uploads are not part of the offer.

Start with reversible, non-sensitive workloads: document conversion, schema validation, embedding generation, synthetic test workloads, and bounded inference. Use a sandboxed worker process or isolated container, per-job scratch storage, explicit cancellation, and a cleanup receipt. Do not sell capacity until metering can reconcile measured usage with a customer-visible job record.

4. Acceptance gates for the next 777 cycles

  1. Manifest: health check succeeds and advertised routes match deployed handlers.
  2. Payment attribution: one provider settlement maps to one known offer and order; replay produces no duplicate entitlement.
  3. Authorization: expired, unpaid, wrong-currency, wrong-offer, and reused-session requests are rejected.
  4. Execution: budget, time, memory, network, and tool restrictions are enforced before the worker starts.
  5. Delivery: an output and digest exist, evaluator criteria pass, and the buyer can retrieve the promised result.
  6. Economic truth: tests and simulated jobs remain labelled TEST or SIMULATED. Only a real independent buyer and settled external payment with verified fulfillment can advance the revenue scoreboard.

5. Turn the specification into compounding components

Each cycle should produce one durable, reviewable unit: a schema, migration, test, worker adapter, runbook, or source-bound market page. A candidate stays internal until tests pass; a public page stays clearly labelled as research until its claims have sources. Deduplicate by content hash and stable artifact ID. Record the parent task, code revision, test evidence, and next dependency so later cycles can inherit the work rather than rewrite it.
