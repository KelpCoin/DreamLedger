# Seven-Day Autonomy Mandate

Status: APPROVED OPERATING PLAN
Scope: BrownEye / DreamLedger / Kelplantis control plane
Duration: seven days from adoption

## Objective

Make Supabase the durable coordination, evidence, handoff, admission, telemetry, and economic-control hub between agent workers, GitHub, deployment systems, and market rails. Normal operation should require zero Biggie intervention.

## Canonical loop

SIGNAL -> ELOHIM/PROPOSER -> TRUTH ORACLE -> GAUNTLET -> POLICY ADMISSION -> GITHUB CI -> HUMAN GATE WHEN REQUIRED -> RELEASE -> MARKET -> FULFILMENT -> MONEY LEDGER -> TELEMETRY -> EVIDENCE -> ORACLE

## Supabase role

Supabase is the authoritative durable control hub. Important state is recorded as structured, auditable records rather than agent prose.

Core coordination surfaces:
- agents and capabilities
- tasks and handoffs
- claims and evidence
- Truth Oracle runs
- Gauntlet runs
- publication admissions
- deployment records
- incidents and kill-switch state
- doctrine and policy
- economic events and outcomes

Agents exchange structured handoffs. Supabase does not grant one agent unrestricted authority over another. Proposal is never authority.

## Seven-day execution sequence

### Day 1: Control hub integrity
Verify and strengthen schemas, identifiers, provenance, RLS, SECURITY DEFINER boundaries, and canonical status transitions. Fix the Truth Oracle context retrieval weakness. Record a durable control-plane baseline.

### Day 2: Agent rendezvous bridge
Establish structured agent-to-agent handoffs through Supabase. Claude remains a first-class consumer. Discover and integrate the existing Grok/other-agent rendezvous mechanism only where evidenced in repository/control-plane records. Do not invent a protocol or dependency from model memory.

### Day 3: Truth Oracle execution
Make reproducible Oracle runs produce durable run records, evidence references, verdicts, hashes, and provenance. Model output alone is never evidence. Wire candidate verification into CI where credentials and execution context permit.

### Day 4: Gauntlet execution
Make adversarial evaluation executable and durable. Test software correctness, security/scope boundaries, evidence completeness, fulfilment feasibility, economic assumptions, and failure modes. A failed or incomplete Gauntlet cannot create an ALLOW receipt.

### Day 5: Closed release loop
Complete the machine gate -> GitHub environment gate -> deployment -> post-deployment verification chain. Preserve exact-SHA binding. Ensure every production exit path is admission-gated. Keep human approval as a distinct GitHub enforcement boundary for HUMAN_REQUIRED risk.

### Day 6: Autonomous operations and recovery
Add incident state, safe-stop/kill-switch semantics, failure telemetry, bounded retries, rollback/recovery paths, and severe-failure notification hooks. Normal routine operation must not depend on Biggie. Dangerous or ambiguous actions quarantine or stop rather than guessing.

### Day 7: Economic proof
Run the complete loop against real opportunities where the existing rails permit it. Measure discovery, verification, Gauntlet survival, release, market response, fulfilment, revenue, net outcome, failures, and human interventions. Produce a seven-day economic control report.

## Economic priority

Revenue-producing verified work outranks architectural polishing. Real market outcomes outrank model confidence. The first genuine stranger payment remains the decisive economic milestone.

## Biggie intervention policy

Biggie is constitutional owner and exception handler, not routine operator. Human intervention is required for high-impact decisions, doctrine/risk-policy changes, genuine ambiguity, security incidents, capital limits, and emergency kill-switch use. Routine admitted execution should proceed unattended.

## Fail-closed rules

- No admission receipt -> no publication.
- UNVERIFIED -> no publication.
- CONTRADICTED -> no publication.
- STALE evidence -> no publication until refreshed.
- GAUNTLET FAIL -> no publication.
- Incomplete evidence -> no publication.
- SHA mismatch -> no publication/deployment.
- Dangerous ambiguity -> quarantine.
- Kill switch -> stop new economic actions while preserving evidence and ledger integrity.

## Definition of success

The system can discover, verify, attack, admit, deploy, measure, fulfil, record economic outcomes, recover from ordinary failures, and continue without Biggie touching the normal path.

Architecture alone is not economic proof. Revenue is established only by observed market transactions.

## `get on with it` operating command

When Biggie says `get on with it`, inspect current control-plane state, identify the highest-value unfinished step, implement it through connected systems, verify it, record proof, fix failures where authorized, and continue. Do not merely return a menu of tasks. Stop only for a genuine external blocker, required human decision, unavailable secret/credential, destructive action requiring approval, or unresolved ambiguity.

## Seven-day scoreboard

- control-hub integrity

- Gauntlet runs completed / passed
- admission receipts issued / denied
- production paths covered by admission
- deployments verified by exact SHA
- incidents / safe stops
- economic opportunities tested
- strangers paying
- gross and net revenue
- human interventions
