DreamLedger / 777 Observatory / Agent Bridge

777 expedition component · 10 October 2026

An open capability exchange, built one verified transaction at a time.

The long-term target is a shared commercial substrate for B2B discovery, agent-to-agent services, reusable digital goods, commerce storefronts, programmatic digital-out-of-home inventory and opt-in compute. The build sequence starts with a narrow paid capability that can actually be fulfilled.

Truth boundary. This is an architecture and execution component, not a claim that marketplace scale, GPU rentals, billboard inventory, live integrations, buyer demand, or revenue have been verified. DreamLedger's current verified external revenue remains NZ$0 until independent settlement, attribution, fulfillment and delivery evidence all reconcile.

One substrate, several exchange surfaces

  • Free B2B discovery: searchable capability profiles, public offer schemas, source-linked supplier facts, comparison tools and request-for-quote structures. Discovery is free; paid execution is separately explicit.
  • Low-cost A2A toll roads: machine-readable manifests, small metered calls, scoped entitlements, budget limits, idempotent requests and signed receipts. Charge for useful execution, not for merely listing an endpoint.
  • Commerce building blocks: storefront and marketplace stencils, checkout adapters, product-data normalization, template packs, reusable word banks, workflow schemas and agent tool adapters. Keep these modular and versioned.
  • Programmatic DOOH: inventory and audience-context discovery first; campaign booking, proof-of-play and settlement only after supply rights, measurement and advertiser billing are demonstrable.
  • Opt-in GPU capacity: a future compute lane for bounded jobs. Never expose the host, unrestricted shell, personal files, raw credentials or arbitrary network access to callers. Use isolated workloads, quotas, timeouts, resource ceilings, job logs, cancellation and explicit owner opt-in.

KPIs that matter

  • Demand: qualified intent events, unique qualified visitors, request-to-offer rate, offer-to-checkout rate and independent buyer count.
  • Economics: settled net proceeds in NZD, refunds/disputes, compute/API/payment costs, contribution margin and revenue per successful fulfilled job.
  • Reliability: settlement-to-entitlement match, duplicate fulfillment count (target zero), successful-call rate, p95 latency, webhook lag, retries and incident recovery time.
  • Compounding: unique accepted artifacts, primary-source coverage, broken-link rate, duplicate rate, indexed useful pages, qualified organic actions and artifact maintenance cost.
  • Human burden: approval minutes per verified outcome and the number of tasks that require identity, consent, payment, legal, public-transmission or irreversible-action approval.

Operating rules

  1. Money first: inspect the existing TOLL-PROBE-50C route before adding a product or provider.
  2. Unknown is not pass. Catalogue entries, successful CI, page publication and checkout creation are not economic outcomes.
  3. One task must return a durable artifact, tests, source/provenance and a concise acceptance result.
  4. Each task is bounded, retryable and idempotent. Failed mechanisms die small; verified mechanisms may grow.
  5. Keep the database outage visible. Any path relying on Supabase for durable orders, atomic quota or fulfillment stays unverified until the database is healthy and the path is tested.
  6. Do not spend money or activate public GPU execution to make the roadmap look complete. First demonstrate demand and positive unit economics.

First expedition acceptance

Inspect the existing manifest, checkout, deployed handler, canonical Stripe settlement webhook, entitlement issuer, scoped key, probe and receipt. Record each as VERIFIED, UNVERIFIED, CONTRADICTED, STALE, TEST or INTERNAL. Fix the smallest broken boundary, then run a harmless negative test and one end-to-end test only when a genuine independent buyer or a clearly segregated test mode is available.
